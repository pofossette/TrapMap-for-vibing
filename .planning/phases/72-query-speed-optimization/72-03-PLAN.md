# PLAN 72-03: Optimize reranking with early termination and caching

## Problem

In `rerank.ts`, `rerankCandidates()` applies multiple heuristics to every candidate, even when they won't affect the final ranking:

```typescript
// rerank.ts line 95-152
const reranked = mergedCandidates.map((candidate) => {
  // Always computed, even if candidate won't make the cut
  if (hasBothChannels(candidate)) { finalScore += bothChannelBoost; }
  if (queryTokens.length > 0 && candidate.tokenMatches.length > 0) { ... }
  if (staleDecayPenalty > 0 && hasStaleDecayState(candidate)) { ... }
  if (config?.boundaryContext) { ... } // Expensive computation
  if (config?.freshnessConfig) { ... } // Creates Date object
  // ...
});
```

Issues:
1. Creates new Date() for every candidate when freshness decay is enabled
2. Computes boundary explanation even for zero-delta cases
3. No early termination for low-scoring candidates

## Solution

Optimize reranking with:

1. **Hoist Date creation**:
   - Create `now` timestamp once outside the loop
   - Pass to `computeFreshnessMultiplier()`

2. **Skip zero-effect computations**:
   - Check boundary delta before calling `buildBoundaryExplanation()`
   - Skip token density calculation if candidate has no matches

3. **Add early termination option**:
   - Add `earlyTerminationThreshold?: number` to RerankConfig
   - Skip candidates whose pre-rerank score is too low to make top-K

4. **Memoize decay calculations**:
   - Cache `computeFreshnessMultiplier()` results for entries with same lastVerifiedAt

## Performance Improvement

- **Date creation**: O(n) → O(1) per query
- **Boundary explanation**: O(n) → O(non-zero-delta count)
- **Freshness calculation**: O(n) → O(unique lastVerifiedAt count)
