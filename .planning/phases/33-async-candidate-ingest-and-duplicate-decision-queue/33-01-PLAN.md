# Plan 33-01: Candidate Submission Types and Store Integration

## Goal
Define the candidate submission record types and integrate them into the existing store infrastructure.

## Context
Phase 33 introduces an asynchronous ingestion boundary. This plan establishes the foundational data structures for candidate submissions and duplicate cases before any processing logic is added.

## Tasks

### Task 1: Create candidate domain types in contracts

<read_first>
- packages/contracts/src/domain/common.ts (for base schemas like entityIdSchema, isoTimestampSchema, lifecycleStateSchema)
- packages/contracts/src/domain/knowledge.ts (for existing AgentReviewResult pattern)
- packages/contracts/src/domain/artifacts.ts (for ArtifactBundle type if exists)
</read_first>

<action>
Create `packages/contracts/src/domain/candidates.ts` with the following schemas:

1. **CandidateStatusSchema** - z.enum with values: 'received', 'queued', 'analyzing', 'duplicate_detected', 'ready_for_review', 'error'

2. **CandidateSourceSchema** - z.enum with values: 'trap', 'skill'

3. **DuplicateMatchTypeSchema** - z.enum with values: 'exact', 'high-overlap', 'semantic-similar'

4. **CandidatePayloadSchema** - object with:
   - `trap` optional: object matching KnowledgeSubmission shape (scope, labels, shortcut, detail, requiredLevel)
   - `skill` optional: object with bundle fields (files array, metadata)

5. **AnalysisSnapshotSchema** - object with:
   - `normalizedAt`: isoTimestampSchema
   - `fingerprint`: z.string() (SHA-256 hash)
   - `keywords`: z.array(z.string())
   - `tokens`: z.array(z.string())

6. **DuplicateOverlapDetailsSchema** - object with:
   - `sharedKeywords`: z.array(z.string())
   - `sharedTokens`: z.array(z.string())
   - `textOverlapPercent`: z.number().min(0).max(100)

7. **DuplicateMatchSchema** - object with:
   - `entityType`: z.enum(['trap', 'skill'])
   - `entityId`: entityIdSchema
   - `entityTitle`: z.string().min(1).max(280)
   - `similarityScore`: z.number().min(0).max(1)
   - `matchType`: DuplicateMatchTypeSchema
   - `overlapDetails`: DuplicateOverlapDetailsSchema

8. **DuplicateCaseSchema** - object with:
   - `id`: entityIdSchema
   - `candidateId`: entityIdSchema
   - `detectedAt`: isoTimestampSchema
   - `detectionVersion`: z.string().min(1) (algorithm version like "1.0.0")
   - `matches`: z.array(DuplicateMatchSchema)
   - `highestSimilarity`: z.number().min(0).max(1)
   - `hasExactDuplicate`: z.boolean()
   - `duplicateType`: z.enum(['exact', 'semantic', 'none'])

9. **CandidateSubmissionSchema** - object with:
   - `id`: entityIdSchema
   - `sourceType`: CandidateSourceSchema
   - `submittedBy`: entityIdSchema (userId)
   - `teamId`: entityIdSchema.nullable()
   - `status`: CandidateStatusSchema
   - `originalPayload`: CandidatePayloadSchema
   - `analysisSnapshot`: AnalysisSnapshotSchema.nullable()
   - `duplicateCase`: DuplicateCaseSchema.nullable()
   - `receivedAt`: isoTimestampSchema
   - `queuedAt`: isoTimestampSchema.nullable()
   - `analyzingAt`: isoTimestampSchema.nullable()
   - `completedAt`: isoTimestampSchema.nullable()
   - `lastError`: z.string().nullable()
   - `retryCount`: z.number().int().min(0)

Export all types using `z.infer<typeof XSchema>`.
</action>

<acceptance_criteria>
- `packages/contracts/src/domain/candidates.ts` exists and contains all 9 schemas listed above
- File contains `CandidateStatus` type export
- File contains `CandidateSubmission` type export
- File contains `DuplicateCase` type export
- File contains `DuplicateMatch` type export
- `CandidateStatusSchema` has exactly 6 enum values: 'received', 'queued', 'analyzing', 'duplicate_detected', 'ready_for_review', 'error'
- `DuplicateMatchTypeSchema` has exactly 3 enum values: 'exact', 'high-overlap', 'semantic-similar'
</acceptance_criteria>

### Task 3: Add candidate store types to server

<read_first>
- packages/server/src/lib/store.ts (full file)
</read_first>

<action>


2. Add new record types that mirror contracts types but with server-side naming:


</action>
