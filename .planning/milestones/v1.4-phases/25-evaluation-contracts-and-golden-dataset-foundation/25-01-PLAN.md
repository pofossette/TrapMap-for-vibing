<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Dataset authors -> shared eval schemas | Untrusted milestone fixtures must be parsed before any future runner uses them |
| Root `evals/` entrypoints -> server endpoint contracts | Eval execution must target current route contracts without silently normalizing different response families |
| Repo docs/entrypoints -> future maintainers | Ambiguous workspace guidance can cause governance and relevance expectations to drift together |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-01 | T | `packages/contracts/src/domain/evals/retrieval.ts` | mitigate | Use strict Zod schemas for scenario actor fields, endpoint enums, tier enums, and expectation groups so malformed or under-specified cases fail at load time. |
| T-25-02 | I | retrieval eval case shape | mitigate | Require separate `relevance` and `governance` sections in every case and explicit endpoint-specific shape assertions so forbidden-result leakage cannot hide inside ranking expectations. |
| T-25-03 | S | endpoint targeting | mitigate | Encode `/v1/retrieval/search` and `/v2/retrieval/search` as explicit literal values and document the v1 compatibility-sensitive path in `evals/retrieval/README.md` to prevent accidental adapter drift. |
| T-25-04 | D | root eval entrypoints | accept | `--dry-run` entrypoints that only load and validate datasets have low denial-of-service risk once they stay file-local and bounded to milestone-owned modules; full execution hardening belongs to Phase 26. |
</threat_model>
