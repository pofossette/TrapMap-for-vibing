# Phase 62-04: Route Integration with KnowledgeRepository

## Objective

Integrate `KnowledgeRepository` into routes and processors following Phase 61's pattern, where routes use the repository directly for knowledge-entry-only mutations instead of `store.transact()`.

## Context

Waves 0-2 created the schemas, repository implementation, and migration tooling. This wave integrates the repository into the routes that perform knowledge mutations (`knowledge.ts`, `traps.ts`, `review.ts`), following the conditional pattern from Phase 61 where `candidateRepo` is used if available.

The ROADMAP specifies: "HybridStore.transact() routes knowledge-entry-only mutations to the repository; mixed mutations fall back to JSONB." The implementation follows Phase 61's direct repository pattern rather than a HybridStore abstraction.

<threat_model>
## Threat Model

| Threat | STRIDE | Mitigation |
|--------|--------|------------|
| Knowledge entry not persisted to PostgreSQL | Tampering | Dual-write ensures both stores updated; primary-first ordering |
| Route regression after integration | Tampering | Comprehensive test coverage; existing tests unchanged |
| Missing repository in request context | Tampering | Graceful fallback to store.transact() when pool unavailable |
</threat_model>

### Task 2: Integrate Repository in knowledge.ts Routes

<read_first>

- packages/server/src/lib/candidates/processor.ts (conditional repository pattern)
</read_first>

**Implementation:**

Update `packages/server/src/routes/knowledge.ts`:

1. Add `knowledgeRepo` to route context access
2. Modify `POST /v1/knowledge` (create entry):
   - Use `knowledgeRepo.nextId()` for ID generation if available
   - Continue using dual-write: create record, push to `data.knowledgeEntries`, AND call `knowledgeRepo.insert()` if available
   - Fallback to `store.nextId()` if repository unavailable

3. Modify `POST /v1/knowledge/:id/resubmit` (resubmit entry):
   - After calling `resubmitKnowledgeEntry()`, also call `knowledgeRepo.appendRevision()` if available
   - This is additive during dual-write period

4. Modify `PATCH /v1/knowledge/:id` (update entry):
   - After calling `updateKnowledgeEntry()`, also update via `knowledgeRepo.updateGovernance()` if available

5. Pattern follows Phase 61's processor.ts:
   ```typescript
   if (services.knowledgeRepo) {
     await services.knowledgeRepo.updateLifecycle(entryId, newState, context);
   } else {
     await services.store.transact(async (txData) => {
       // existing JSONB logic
     });
   }
   ```

## Notes

This wave implements the ROADMAP criterion #5: "HybridStore.transact() routes knowledge-entry-only mutations to the repository; mixed mutations fall back to JSONB."

The implementation uses the conditional repository pattern from Phase 61 rather than a HybridStore abstraction because:
1. Phase 61's pattern is proven and tested
2. Routes have fine-grained control over when to use repository vs JSONB
3. The dual-write period requires both paths to work simultaneously
4. Phase 63 will remove the JSONB path entirely
