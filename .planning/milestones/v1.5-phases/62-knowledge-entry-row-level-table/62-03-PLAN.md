# Phase 62-03: Migration Script and Module Integration

## Objective

Create a migration script to backfill existing knowledge entries from the JSONB snapshot to the new relational tables, and ensure the knowledge module exports are complete.

## Context

Waves 0-1 created the schemas and repository implementation. This wave creates the migration tooling to move existing data from JSONB to the new tables, following the same pattern as Phase 61's migrate-candidates.ts.

<threat_model>
## Threat Model

| Threat | STRIDE | Mitigation |
|--------|--------|------------|
| Data loss during migration | Tampering | Migration is additive-only; JSONB data preserved until Phase 63 |
| Data divergence after migration | Tampering | Dual-write ensures both stores are updated; migration skips already-migrated entries |
| Migration script SQL injection | Tampering | Use repository methods (parameterized) instead of raw SQL for data insertion |
</threat_model>

## Tasks

### Task 1: Create Migration Script

<read_first>
- packages/server/src/lib/persistence/migrate-candidates.ts (migration pattern)
- packages/server/src/lib/knowledge/pg-repository.ts (PgKnowledgeRepository)
- packages/server/src/lib/store.ts (KnowledgeRecord type)
</read_first>

**Implementation:**

Create `packages/server/src/lib/persistence/migrate-knowledge.ts`:

1. Define `MigrationConfig` interface:
   ```typescript
   export interface MigrationConfig {
     pool: Pool;
     store: SkillShareerStore;
     dryRun?: boolean;
     batchSize?: number;
     onProgress?: (info: { processed: number; total: number; entryId: string }) => void;
   }
   ```

2. Define `MigrationResult` interface:
   ```typescript
   export interface MigrationResult {
     totalEntries: number;
     migrated: number;
     skipped: number;
     errors: MigrationError[];
     durationMs: number;
   }

   export interface MigrationError {
     entryId: string;
     error: string;
   }
   ```

3. Implement `migrateKnowledgeEntries(config)` function:
   - Read `data.knowledgeEntries` from store snapshot
   - For each entry:
     - Check if already exists in relational table (idempotent)
     - If not, insert via PgKnowledgeRepository
   - Report progress via callback
   - Collect and return errors without stopping
   - Support dry-run mode

4. Handle nested data correctly:
   - Each entry has history[] (revisions) to insert
   - Each entry has lifecycleHistory[] (events) to insert
   - All must be inserted in transaction for consistency

5. Preserve existing IDs:
   - Migration uses existing entry IDs from JSONB (not SEQUENCE-generated)
   - SEQUENCE is only used for new entries created post-migration
   - Ensure SEQUENCE is set to max(existing_ids) + 1 after migration

Create `packages/server/src/lib/persistence/migrate-knowledge.test.ts`:

1. Test dry-run mode:
   - Create store with test knowledge entries
   - Run migration with dryRun: true
   - Verify skipped count equals total count
   - Verify no data written to tables

2. Test basic migration:
   - Create store with test knowledge entries
   - Run migration
   - Verify migrated count matches
   - Verify entries can be retrieved from repository

3. Test idempotent migration:
   - Run migration twice
   - Verify second run has skipped count = total
   - Verify no duplicate entries

4. Test error handling:
   - Create entry with invalid data (e.g., missing required field)
   - Run migration
   - Verify error recorded, other entries still processed

5. Test nested data migration:
   - Create entry with multiple revisions
   - Create entry with multiple lifecycle events
   - Verify all nested data migrated correctly

6. Test SEQUENCE synchronization:
   - Migrate entries with known IDs
   - Call nextId() after migration
   - Verify generated ID is greater than all migrated IDs
