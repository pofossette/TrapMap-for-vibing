# TrapMap WebUI 页面版式重构指南

## 1. 文档目的

本文档基于以下两份输入，给出 TrapMap WebUI 的页面版式重构指南：

- [`packages/web-panel/docs/requirements.md`](../../packages/web-panel/docs/requirements.md)
- [`temp/index.html`](../../temp/index.html)

本指南不替代需求文档。需求文档负责定义“要做哪些页面和功能”，本指南负责回答“这些页面应如何重构版式、保留什么、替换什么、优先解决什么问题”。

适用对象：

- 平面设计
- 交互设计
- 前端实现
- 后续 WebUI 重构评审

## 2. 当前原型的定位判断

`temp/index.html` 已经不是纯空白草图，它已经给出了第一版较完整的控制台原型，包含：

- 左侧固定导航
- 顶部全局搜索与环境状态条
- 首页数据展板
- 审核队列
- 审核详情工作台
- 工件总览
- Trap 图谱
- Skill 图谱
- 活动审计
- G6 图交互雏形

这意味着本轮重构不是“从零设计”，而是“把现有原型从能看，重构为能作为正式产品设计基线”。

## 3. 对 `temp/index.html` 的现状判断

结合当前原型和需求文档，现状可概括为：

### 3.1 已经做对的部分

- 信息架构方向基本正确，已经对应了需求稿里的主要页面。
- 首页具备数据展板雏形，已经包含健康状态、核心指标、图谱预览、待审核数。
- 图谱页已经采用三栏结构，符合后续 Trap Graph / Skill Graph 的主工作流。
- 审核详情页已经具备“主工作区 + 右侧操作 / 时间线”的工作台思路。
- G6 已经接入，且已经实现了拖拽后固定位置的基本交互雏形。
- 视觉语言已经有一致性：暗色底、蓝色主强调、圆角卡片、细边框。

### 3.2 当前存在的主要问题

- 首页仍偏“指标堆叠”，没有形成真正的首屏主次关系。
- 首页图谱预览区还不够强，未成为首屏视觉焦点。
- 各页面虽然已经存在，但“页面目标”与“版式重点”还没有完全拉开，导致多个页面看起来像同一种卡片 + 表格拼装。
- 审核页、工件页、图谱页之间的跳转关系还不够明确，缺少统一入口和回路。
- `temp/index.html` 使用了较强的“后台控制台模板感”，但 TrapMap 实际上是“治理 + 结构调试”混合产品，需要更鲜明的图谱产品气质。
- Skill 图谱页虽然区分了 derivation / semantic 模式，但在版式上还没有把“派生检查”与“图谱检查”拉开层次。
- Inspector 的信息承载潜力已经有了，但当前还是偏“信息列出”，未形成高质量的结构化阅读体验。

## 4. 本轮重构的总原则

### 4.1 先拉开页面角色，再细化视觉风格

本轮优先级不是先做装饰，而是先把每个页面的职责、阅读路径和操作路径拉开。用户应在 3 秒内分辨：

- 首页是总览入口
- 审核队列是“筛选和派发”页
- 审核详情是“处理和决策”页
- 工件总览是“对象目录”页
- Trap 图谱是“陷阱关系检查”页
- Skill 图谱是“派生物与语义图检查”页
- 活动审计是“回溯与复盘”页

### 4.2 首屏必须突出“图谱预览 + 系统态”

TrapMap 的产品辨识度不应只是一个普通后台。首页必须同时表达：

- 它是一个在运行中的治理系统
- 它也是一个以图谱和派生结构为核心的知识系统

因此首页不能只放数字卡片，必须把图谱预览做成真正的视觉主角之一。

### 4.3 图谱页必须像开发者工具，而不是内容页

Trap Graph 和 Skill Graph 页面不应沿用普通内容管理页的排版逻辑。它们应更像：

- Vue Devtools
- React Devtools
- 数据建模或可观测性产品中的结构检查器

因此图谱页要强调：

- 工具栏
- 过滤器
- 画布
- Inspector
- 聚焦 / 高亮 / 固定节点等可操作状态

### 4.4 审核流与图谱流必须形成闭环

从审核详情页应能跳到相关工件与图谱。
从工件页应能进入 Skill Graph / Trap Graph。
从图谱页应能回到来源记录。

如果这条链路不完整，页面再漂亮也只是碎片。

### 4.5 优先抽离公共组件，而不是按页面重复拼装

TrapMap 的核心对象在多个页面中重复出现：

- trap
- skill capsule
- artifact
- graph document
- 风险状态
- scope / required level

如果每个页面各自定义一套卡片、标签和摘要块，最终会出现：

- 同一个对象在不同页面长得不一样
- 交互入口不一致
- 设计难以统一
- 前端实现难以维护

因此本轮重构必须把“公共组件抽离”作为页面重构的一部分，而不是后置优化项。

### 4.6 优先使用 HeroUI 组件组合，而不是手搓外壳

公共组件的首选实现方式不是完全自定义 DOM，而是优先基于 HeroUI 现有组件组合：

- `Card`
- `Chip`
- `Button`
- `Tabs`
- `Drawer`
- `Table`
- `Tooltip`
- `Dropdown`

原则是：

- 能用 HeroUI 就先用 HeroUI
- 只在 TrapMap 有明确业务辨识度的部分做轻定制
- 抽离组件时保留 HeroUI 的默认交互反馈和可访问性

## 5. 公共组件抽离策略

本节用于约束后续设计和前端实现：先定义可复用对象卡，再把它们布置到页面中，而不是先做页面后补组件。

### 5.1 必须优先抽离的公共组件

建议至少先抽离以下组件：

- `TrapPreviewCard`
- `SkillCapsulePreviewCard`
- `ArtifactPreviewCard`
- `GraphPreviewCard`
- `HealthStatusCard`
- `RiskStatusChipGroup`
- `MetaInfoCard`
- `InspectorSectionCard`
- `EntityQuickActions`

### 5.2 抽离顺序建议

先抽离：

1. 状态与标签类组件
2. 预览卡片类组件
3. Inspector 分组卡组件
4. 页面组合模块

原因：

- 状态组件决定整个系统的语义一致性
- 预览卡片是首页、工件页、图谱页之间最常复用的内容单元
- Inspector 分组卡决定图谱页和详情页的阅读质量

### 5.3 组件设计原则

每个公共组件都应满足：

- 有明确主信息区
- 有明确辅助信息区
- 有统一的主动作 / 次动作位置
- 能在紧凑模式与标准模式之间切换
- 尽量通过 props 控制变体，而不是复制多个近似组件

## 6. 核心公共组件说明

## 6.1 TrapPreviewCard

### 使用场景

- 首页待处理事项区
- 首页 Trap 图预览旁的重点 trap 摘要
- 工件总览页中的 trap 类型记录
- Trap 图谱页右侧相关节点摘要

### 承载信息

- trap 标题
- trap ID
- 风险等级
- scope
- required level
- 最近更新时间或 revision
- 相关 cue / mitigation 数量摘要

### 交互要求

- 主点击进入 trap 详情或聚焦图谱
- 次动作支持“查看图谱”
- hover 时显示更多摘要或 tooltip

### HeroUI 实现建议

优先使用：

- `Card`
- `Chip`
- `Button`
- `Tooltip`

不建议单独重写整个外壳。重点通过 HeroUI Card 的 header / body / footer 组合完成。

## 6.2 SkillCapsulePreviewCard

### 使用场景

- 首页 Skill 图预览区
- 工件详情中的 capsule 列表
- Skill 图谱页左侧 capsule 聚焦列表
- Inspector 中 related capsules 摘要区

### 承载信息

- capsule 标题或 capsule ID
- situation
- problem
- goal
- labels
- sourcePaths 数量
- required level

### 交互要求

- 主点击进入该 capsule 的聚焦图视图
- 支持“查看派生详情”
- 支持“高亮相关节点”

### HeroUI 实现建议

优先使用：

- `Card`
- `Chip`
- `Button`

建议提供两种密度：

- `compact`
- `default`

其中 `compact` 用于侧栏和列表，`default` 用于详情与首页重点块。

## 6.3 ArtifactPreviewCard

### 使用场景

- 工件总览页主列表
- 首页最近更新工件区
- Skill 图谱页 artifact 选择结果区
- 审核详情页相关工件引用区

### 承载信息

- artifact ID
- title
- lifecycle state
- revision
- capsule count
- scope
- required level

### 交互要求

- 主点击打开详情抽屉
- 次动作：
  - 打开 Skill 图谱
  - 查看派生信息

### HeroUI 实现建议

优先基于：

- `Card`
- `Chip`
- `Button`
- `Dropdown`（如果动作较多）

如果该页面本身更适合表格，则卡片形态只作为详情摘要和首页模块复用，不强行在所有页面都使用卡片。

## 6.4 GraphPreviewCard

### 使用场景

- 首页 Trap 图预览
- 首页 Skill 图预览
- 工件页中的图摘要模块

### 承载信息

- 图类型
- 缩略预览画布
- 节点数
- 边数
- 最近更新时间
- 主入口按钮

### 交互要求

- 点击进入完整图谱页
- 点击次按钮进入聚焦视图

### HeroUI 实现建议

外壳优先基于 `Card`，但画布区域允许自定义更强的 TrapMap 风格。

原则：

- 卡片框架用 HeroUI
- 预览画布用自定义内容
- 底部动作继续用 HeroUI Button

## 6.5 HealthStatusCard

### 使用场景

- 首页系统健康区
- 图谱页左栏运行状态区
- 审核详情页的当前状态摘要

### 承载信息

- 状态名称
- 当前状态值
- 状态说明
- 最近检查时间

### HeroUI 实现建议

优先使用：

- `Card`
- `Chip`

不要自己重造一套状态块。

## 6.6 InspectorSectionCard

### 使用场景

- Trap 图谱页右栏
- Skill 图谱页右栏
- 工件详情抽屉
- 审核详情右栏

### 承载信息

每一块只承载一类信息：

- 基本信息
- 派生信息
- 图信息
- 治理信息
- 快捷动作

### HeroUI 实现建议

优先使用：

- `Card`
- `Divider`
- `Button`

每个 Inspector section 都应是统一外观的分组卡，而不是页面里零散的标题 + 文本块。

## 7. 组件变体与复用规则

### 7.1 不同页面允许不同密度，不允许不同语义

同一个组件可以有：

- `compact`
- `default`
- `emphasized`

但不允许在不同页面改变它的语义结构。

例如：

- `ArtifactPreviewCard` 在首页可以更强调标题和状态
- 在侧栏可以更紧凑
- 但都必须保留同一组核心字段和动作位置

### 7.2 公共组件优先复用动作区布局

预览卡片建议统一动作规则：

- 左下放次动作
- 右下放主动作

或：

- 底部左侧信息补充
- 底部右侧主操作

不要让每张卡片的按钮位置都不同。

### 7.3 状态展示统一通过 HeroUI 语义组件表达

以下信息尽量统一用 HeroUI `Chip` 或接近形态表达：

- 风险等级
- lifecycle state
- scope
- required level
- graph backend 状态
- readiness / liveness 结果

## 8. 当前原型中建议保留的版式骨架

以下骨架建议保留，不需要推倒重来：

### 5.1 全局壳层

保留：

- 左侧固定导航
- 顶部全局搜索和系统状态条
- 主内容区滚动

理由：

- 这套结构已经适合管理台产品
- 与需求稿中的一级页面结构吻合
- 后续易于扩展更多页面和全局状态

### 5.2 图谱页三栏结构

保留：

- 左栏过滤器
- 中间画布
- 右栏 Inspector

理由：

- 这是图谱调试最合适的工作流结构
- 已经和需求文档保持一致
- 后续只需强化层次，不需要改架构

### 5.3 审核详情页工作台结构

保留：

- 主内容区
- 右侧辅助区

理由：

- 审核详情天然适合“内容 + 操作 / 审计”并列
- JSON 编辑器也适合放在主区下半部分

## 9. 当前原型中建议重构的版式问题

### 6.1 首页不应只是四个指标卡 + 两个预览盒子

当前首页已经有数据卡片与图谱预览，但主次还不够清晰。重构后应变成：

- 第一视觉层：系统状态与图谱预览
- 第二视觉层：库规模与待处理事项
- 第三视觉层：异常与快捷入口

不建议继续让首页的重点停留在平均化的小卡片上。

### 6.2 工件总览页不能只像一个卡片列表

当前工件页更像“对象卡片墙”。重构后需要更强的“目录页”属性：

- 左上明确是搜索与过滤
- 中间明确是对象列表
- 右侧或抽屉明确是摘要详情
- 跳图谱入口要变成强动作，而不是附属信息

### 6.3 Skill 图谱页要更强区分两种视图模式

当前 prototype 已有 `derivation` / `semantic` 切换，但它们还像同一套页面切不同数据。

重构后应做到：

- `Derivation View` 更强调层级、来源路径、文件与派生物的关系
- `Semantic Graph View` 更强调语义节点、边类型、局部聚焦和图探索

也就是说，两种模式不只是按钮切换，而应有明显不同的信息重心。

### 6.4 Inspector 需要从“字段罗列”升级为“结构化阅读”

当前右侧信息面板方向是对的，但后续不能只把字段一条条列出来。要分块：

- 基本信息
- 派生信息
- 治理信息
- 图信息
- 可执行动作

## 10. 按页面的版式重构指南

## 11. 首页数据展板重构指南

### 8.1 页面结构建议

首页建议采用“上强下稳”的三段结构：

1. 顶部总览带
2. 中部双核心区
3. 底部运营区

### 8.2 顶部总览带

建议放置：

- 页面标题与一句话说明
- deployment profile
- 当前版本 / build
- 最近健康检查时间
- 当前系统状态总标签

这一带应更像“控制台抬头”，高度克制，不要占太多垂直空间。

### 8.3 中部双核心区

首页中部应成为首屏核心，分为左右两大块：

- 左侧：系统健康与待处理事项
- 右侧：Trap 图 / Skill 图预览

建议比例：

- 左 5 / 右 7
- 或左 4 / 右 8

原因：

- 图谱预览是 TrapMap 的识别性资产，应该比普通数字卡片更显眼

### 8.4 系统健康与待处理事项区

左侧建议分成上下两块：

- 上：健康状态卡
- 下：待处理工作卡

健康状态卡应重点突出：

- readiness
- liveness
- degraded dependencies
- graph backend
- capsule index health

待处理工作卡应重点突出：

- pending review
- high risk pending
- longest waiting
- candidate backlog

### 8.5 图谱预览区

右侧建议上下排布两个大预览块：

- Trap 图预览
- Skill 图预览

每个预览块都不应只是一个黑盒子占位，而要包含：

- 小型关系结构缩略图
- 节点数 / 边数
- 最近更新说明
- 一个主按钮：进入完整图谱页
- 一个次按钮：查看聚焦子图

### 8.6 底部运营区

底部建议放两类内容：

- 数据规模展板
- 最近异常 / 快捷入口

数据规模展板展示：

- trap 总数
- skill artifact 总数
- capsule 总数
- graph document 总数

最近异常区展示：

- warnings
- incidents
- 最近失败任务

快捷入口区展示：

- 审核队列
- 工件总览
- Trap 图谱
- Skill 图谱
- 活动审计

## 12. 审核队列页重构指南

### 9.1 页面结构建议

审核队列页建议采用“三层顺序”：

1. 顶部标题与统计
2. 过滤与搜索工具带
3. 主列表区

### 9.2 版式重点

- 顶部不要太厚，重点让给列表和过滤器
- 过滤栏要横向清晰，不要做成过多折叠交互
- 列表优先使用表格视图，而不是大卡片

### 9.3 列表重点

必须让用户快速看出：

- 哪些是高风险
- 哪些等待最久
- 哪些已指派 / 未指派
- 点击后去哪里

因此建议强化：

- 风险 badge
- 状态 badge
- 等待时长列
- 行 hover 与 active 状态

## 13. 审核详情页重构指南

### 10.1 页面结构建议

保持当前“主区 + 右区”的工作台结构，但要重排阅读顺序。

建议主区从上到下为：

- 头部摘要
- metadata summary
- warnings / related references
- JSON 编辑器

右区从上到下为：

- 决策操作卡
- 当前状态卡
- 审计时间线

### 10.2 重构重点

- 把“决策动作”从散落按钮，升级为一个清晰的决策面板
- JSON 编辑器继续保留技术感，但需要更明显的错误提示与 unsaved 状态
- 右区时间线应更清楚地服务“先看什么、后做什么”

## 14. 工件总览页重构指南

### 11.1 页面结构建议

建议采用：

- 顶部标题和统计
- 搜索 / 过滤工具带
- 中间对象列表
- 右侧详情抽屉或点击后右滑面板

### 11.2 重构重点

- 页面应该更像“对象目录”而不是“信息海报”
- 列表项的主要动作必须明确：
  - 查看详情
  - 打开 Trap 图谱
  - 打开 Skill 图谱
- 对于 skill artifact，应突出 capsule 数量、scope、revision、状态

### 11.3 详情抽屉建议

工件详情抽屉应分块：

- 基本信息
- 派生摘要
- 图摘要
- 治理信息
- 快捷动作

## 15. Trap 图谱页重构指南

### 12.1 页面结构建议

继续保留当前 `280 / 1fr / 340` 一类的三栏结构思路，但增强工具感。

建议：

- 左栏更像“过滤与视图控制台”
- 中间更像“图谱工作画布”
- 右栏更像“节点 / 边检查器”

### 12.2 左栏内容

应包含：

- source 选择
- node type filter
- edge type filter
- hard edge only
- neighborhood depth
- scope / required level

### 12.3 中间画布

保留 G6 画布，强调：

- 默认 fit view
- hover 邻接高亮
- click 聚焦
- drag-fixed 行为
- 清晰的选中状态

### 12.4 右栏 Inspector

建议分块：

- Trap 基本信息
- 图证据信息
- 相关节点列表
- 来源跳转动作

## 16. Skill 图谱页重构指南

### 13.1 页面结构建议

Skill 图谱页仍采用三栏，但它比 Trap 图谱页更复杂，因为要同时容纳 `Derivation View` 与 `Semantic Graph View`。

因此建议在页面上方加入更明确的模式带：

- artifact 选择器
- 视图模式切换
- revision 切换

### 13.2 Derivation View 重构建议

这个模式应突出“从 artifact 到 profile / capsules / references / scripts / assets 的拆解关系”。

版式重点：

- 中心节点是 artifact
- 第一层是 profile / manifest / capsules
- 第二层是 reference / asset / script

视觉风格应更偏结构层级，不必过度强调语义关系。

### 13.3 Semantic Graph View 重构建议

这个模式应突出“skill 如何与 cue、tool、environment、prerequisite、mitigation 发生关系”。

版式重点：

- skill / capsule 是主焦点
- 关系边要更显眼
- 支持聚焦一个 capsule 的局部图

### 13.4 右侧 Inspector 重构建议

右栏要成为 Skill 图谱页的核心价值承载区，必须以“分组面板”而不是“字段堆砌”方式呈现：

- 基本信息
- Profile 信息
- Capsule 信息
- Manifest 信息
- Script / Reference / Asset 信息
- 相关动作

## 17. 活动审计页重构指南

### 14.1 页面结构建议

建议采用：

- 顶部标题与过滤器
- 中部审计列表
- 可选右侧详情抽屉

### 14.2 重构重点

- 审计页应强调“可追踪性”，而不是做成普通日志表
- 每条记录都应能清楚看到 actor、action、target、time、reason
- 应支持跳回来源记录

## 18. 视觉语言重构建议

## 19. 建议保留的视觉基因

当前原型中以下视觉基因建议保留：

- 暗色工作台基底
- 冷色高亮主色
- 细边框卡片体系
- 圆角但不浮夸
- 技术性较强的 monospace 信息块

## 20. 建议调整的视觉问题

### 17.1 降低“通用 SaaS 后台模板感”

当前原型的黑底蓝边方向是对的，但还偏通用后台。需要加入更明确的图谱产品特征：

- 首页图谱预览更突出
- 图谱页更强调工作画布
- Inspector 更强调技术细节阅读

### 17.2 减少平均化卡片

不是每个信息都应该长得一样重要。应拉开：

- 主卡
- 次卡
- 工具卡
- 状态卡

### 17.3 强化页面记忆点

每页至少要有一个“视觉锚点”：

- 首页：双图谱预览
- 审核详情：JSON 工作区
- Trap 图谱：关系画布
- Skill 图谱：模式切换 + 派生 Inspector

## 21. 与 HeroUI 默认风格的结合原则

本轮重构不应把 HeroUI 只当作“可有可无的组件来源”，而应把它作为基础设计系统使用，再在其上叠加 TrapMap 的技术型工作台气质。

核心原则：

- 优先使用 HeroUI 的默认组件结构和交互反馈
- 优先通过主题变量、语义色、圆角、边框、阴影做轻度定制
- 不要为了“做得特别”而推翻 HeroUI 的默认尺寸、间距、焦点态和可访问性
- 复杂的品牌感应集中在首页图谱预览、图谱画布和 Inspector，而不是所有按钮、输入框、表格都重写

### 18.1 应保留 HeroUI 默认风格的部分

以下部分建议尽量贴近 HeroUI 默认风格：

- Button
- Input
- Select
- Tabs
- Card
- Table
- Drawer
- Modal
- Chip / Badge
- Dropdown
- Tooltip

原因：

- 这些组件本身就是“操作密集型后台”的基础件
- HeroUI 默认态已经比较适合中后台产品
- 保留默认交互能减少自定义维护成本

### 18.2 应做 TrapMap 化增强的部分

以下部分建议在 HeroUI 基础上做明显的 TrapMap 风格增强：

- 首页图谱预览容器
- Trap Graph / Skill Graph 的画布区域
- Inspector 内的信息分组卡
- JSON 编辑器区域
- 健康状态卡与风险状态卡

原因：

- 这些区域是 TrapMap 的产品识别点
- 这里承担的是“图谱调试”和“治理检查”语义，不能过度通用化

### 18.3 不建议的做法

- 不要把所有 HeroUI 组件都改成完全自定义的圆角、边框和 hover 体系
- 不要让首页所有卡片都长得像图谱卡
- 不要在图谱页塞入过度花哨的背景、渐变和装饰光效
- 不要破坏 HeroUI 默认的焦点态、禁用态和点击反馈

## 22. HeroUI 主题落地建议

### 19.1 主题方向

建议采用“基于 HeroUI 默认暗色主题的轻定制”，而不是完全脱离其默认主题体系。

主题关键词：

- 深色工作台
- 冷色主强调
- 低饱和边框
- 高信息密度
- 稳定、克制、技术型

### 19.2 颜色策略

建议按三层组织颜色：

- 基础层：背景、表面、边框、文字
- 语义层：success / warning / danger / primary
- 产品层：TrapMap 图谱高亮色

其中：

- 基础层尽量复用 HeroUI 暗色体系
- 语义层复用 HeroUI 默认语义色
- 产品层仅在图谱预览、选中态、关键入口中增强

建议：

- `primary` 继续偏蓝
- `success` 用于健康通过
- `warning` 用于待关注
- `danger` 用于 critical 风险与失败任务

### 19.3 圆角与边框策略

建议遵循 HeroUI 默认卡片和输入风格，统一为中等圆角，不要做过硬或过软：

- 普通操作组件：沿用 HeroUI 默认圆角等级
- 图谱预览和画布容器：允许略大一档
- Inspector 分组卡：与 Card 保持一致

边框建议：

- 常规组件使用低对比边框
- 当前选中块或高风险块才提高边框对比度

### 19.4 阴影策略

TrapMap 不应依赖重阴影塑造层次。

建议：

- HeroUI 默认轻阴影只用于悬浮或抽屉
- 常规卡片以边框和背景层次为主
- 图谱画布区域不依赖阴影，依赖结构分隔

## 23. 按页面的 HeroUI 组件映射建议

这一节用于把“页面需求”映射到更具体的 HeroUI 组件使用方式，便于设计和前端协同。

### 20.1 首页数据展板

建议组件：

- 页面容器：`Card` + 自定义 section wrapper
- 顶部状态标签：`Chip`
- 健康状态卡：`Card`
- 快捷入口：`Button`
- 异常提示：`Alert` 风格容器或 `Card` 变体
- 图谱预览区外壳：`Card`

风格建议：

- 首页的健康卡和数据卡仍然用 HeroUI Card 体系
- 但图谱预览区要做更大的留白和更强的层次，不能只是普通 Card
- 快捷入口按钮优先使用 HeroUI 默认 Button 样式，只在主入口上用 `primary`

### 20.2 审核队列页

建议组件：

- 筛选区：`Input`、`Select`、`Dropdown`
- 列表区：`Table`
- 风险状态：`Chip`
- 批量或快捷动作：`Button`

风格建议：

- 这一页应尽量贴近 HeroUI 默认中后台审美
- 重点放在可扫描性，不做过多图形化装饰
- 风险和状态通过 `Chip` 做强对比即可

### 20.3 审核详情页

建议组件：

- 摘要区：`Card`
- 警告区：`Card` 或 `Alert` 风格块
- 右侧操作区：`Card`
- 时间线可使用自定义布局，但按钮、输入和确认弹窗继续使用 HeroUI
- 确认动作：`Modal`
- JSON 编辑器外壳：`Card`

风格建议：

- 审核详情页的工作台感主要来自布局，而不是组件造型
- 操作按钮保持 HeroUI 默认风格
- JSON 编辑器可更技术化，但外层仍应被 HeroUI Card 包裹，保证整体一致

### 20.4 工件总览页

建议组件：

- 搜索与过滤：`Input`、`Select`
- 工件列表：优先 `Table`，次选列表卡
- 详情抽屉：`Drawer`
- 标签字段：`Chip`
- 跳图谱入口：`Button`

风格建议：

- 工件页应该最接近“HeroUI 默认中后台页面”
- 不建议把工件页做得过分图谱化
- 图谱能力通过详情抽屉内的“快捷动作”体现，而不是列表本身承担

### 20.5 Trap 图谱页

建议组件：

- 左栏过滤器：`Card` + `Select` + `Checkbox` + `Switch`
- 顶部工具栏：`Button`、`Input`、`Dropdown`
- 右侧 Inspector：多个 `Card` 分组

风格建议：

- 图谱页的 HeroUI 存在感应退到二线，主角是 G6 画布
- 但工具栏、过滤器、Inspector 仍必须保持 HeroUI 的交互一致性
- 不要在画布中复刻 HeroUI 卡片感，画布应是更纯粹的工作区

### 20.6 Skill 图谱页

建议组件：

- 顶部模式切换：`Tabs`
- artifact selector：`Autocomplete` 或 `Select`
- 左栏过滤器：`Card` + 表单控件
- 右侧 Inspector：分组 `Card`
- 二级动作：`Button`

风格建议：

- `Tabs` 是这一页与 HeroUI 默认风格结合的重点组件之一
- `Derivation View` 和 `Semantic Graph View` 的差异，优先通过页面信息结构体现，而不是只靠换皮
- Inspector 内的分组卡应比首页更紧凑，强调工具感

### 20.7 活动审计页

建议组件：

- 过滤器：`Input`、`Select`
- 列表：`Table`
- 详情抽屉：`Drawer`

风格建议：

- 审计页应尽量接近 HeroUI 默认数据页风格
- 这是整个系统中最不需要“个性化造型”的页面之一

## 24. 组件级细化建议

### 21.1 Button

建议：

- 主动作使用 HeroUI `primary`
- 危险动作使用 `danger`
- 次级动作尽量使用 `default` 或 `flat`
- 图谱页工具按钮尽量小型化，但不自造一套非 HeroUI 风格

### 21.2 Card

建议：

- 首页卡片使用 HeroUI Card 作为基础容器
- 图谱页 Inspector 使用更紧凑的 Card
- 不同卡片的差异主要通过内容密度和分组，而不是改造出完全不同的壳

### 21.3 Table

建议：

- 审核队列和活动审计优先用 Table
- 通过行高、状态 Chip、hover 态建立可读性
- 不建议自写过重的条纹、复杂分隔或多彩背景

### 21.4 Drawer

建议：

- 工件详情、审计详情适合用 Drawer
- 不建议在首页使用 Drawer 作为核心交互
- Drawer 内部信息要继续分组，不要变成长文档

### 21.5 Tabs

建议：

- Skill 图谱页使用 Tabs 切换 derivation / semantic
- Tabs 风格尽量贴近 HeroUI 默认，不另造胶囊切换器

### 21.6 Chip

建议：

- 风险等级
- 状态
- scope
- required level

这些字段优先用 Chip 表达，而不是纯文本标签。

## 25. 响应式与密度建议

虽然 WebUI 主要面向桌面端，但仍需保留基本响应式规则。

### 22.1 桌面端优先

建议默认设计基线：

- 1440 宽及以上为主工作宽度
- 1280 宽仍需完整可用

### 22.2 小屏处理

当宽度不足时：

- 首页双核心区改为上下堆叠
- 工件详情抽屉可全宽展开
- 图谱页左右栏可折叠

### 22.3 信息密度

TrapMap 是工作台，不是营销站。应允许较高信息密度，但必须有秩序：

- 首页中等密度
- 审核与工件页中高密度
- 图谱页高密度，但信息要分层

## 26. 图交互实现约束

图形库统一使用 `G6`，交互基线采用：

- `https://g6.antv.antgroup.com/examples/layout/force-directed/#drag-fixed`

必须保留：

- 节点拖拽
- 拖拽后固定位置
- 取消固定
- 画布缩放
- 画布平移
- 点击节点
- 点击边
- fit view

在重构版式时，不能为了视觉整洁牺牲这些交互。

## 27. 实施顺序建议

建议按以下顺序推进：

1. 先稳定全局壳层和首页数据展板
2. 再重构审核队列与审核详情
3. 再重构工件总览
4. 最后细化 Trap 图谱与 Skill 图谱

原因：

- 首页决定整体设计语言
- 审核页决定治理工作流是否顺手
- 工件页决定对象目录是否清晰
- 图谱页复杂度最高，应建立在前面语言统一之后再收尾

## 28. 验收口径

这轮版式重构完成后，应满足以下判断标准：

- 用户打开首页后，能立刻看懂系统状态、库规模和图谱入口
- 用户能自然地从首页进入审核流、工件流、图谱流
- 审核详情页的主次关系明显，处理动作不混乱
- 工件页看起来像对象目录，而不是零散卡片集合
- Trap 图谱页看起来像图结构检查器
- Skill 图谱页能明显区分 derivation 与 semantic 两种工作模式
- Inspector 的信息阅读体验明显优于当前原型
- 全局风格保留技术感，但减少普通后台模板感
